# LinuxForge Core V49.1 — Runtime Identity Hardening

## Milestone

**M1 — Runtime Identity & Multi-Tenant Isolation** hardening pass.

This release closes the runtime-identity concurrency/FK race discovered in V49 and moves the security-critical identity/verification writes behind service-role-only database functions.

## Security invariants now enforced

1. **One logical lab instance → one canonical `runtime_id`.**
2. `lab_instances` is the authoritative source for lab ownership, learner ownership, node placement, and binding generation.
3. Runtime identity creation/refresh is serialized by locking the authoritative `lab_instances` row.
4. Existing `runtime_id` values are never replaced during refresh.
5. Same-generation calls are idempotent; they do not rotate credentials or expiry.
6. Binding generations may move forward but cannot move backward.
7. A `REVOKED` or `QUARANTINED` identity cannot be silently reactivated.
8. Isolation verification is persisted only when the database confirms the supplied runtime identity is the canonical identity for the instance and that ownership/generation still match.
9. The isolation-verification FK remains intact; no FK weakening or error-swallowing workaround was introduced.
10. Browser code never receives direct access to `lab_runtime_identities`; sensitive operations remain server-only.

## Implementation

### Database

`supabase/migrations/20260929000000_v49_1_runtime_identity_hardening.sql`

Adds service-role-only functions:

- `v49_ensure_runtime_identity(...)`
- `v49_persist_isolation_verification(...)`

The first function performs canonical identity creation/refresh under database locking. The second locks the canonical identity before inserting the FK-bound isolation verification.

### Server control plane

`src/lib/forge/sandbox/runtime-identity.server.ts`

`ensureRuntimeIdentity()` now resolves identity exclusively through the hardened database function and rejects any returned ownership/generation mismatch.

`verifyAndPersistRuntimeIsolation()` now verifies runtime-health identity fields before persistence and delegates the final canonical-identity check to the service-role-only database function.

### Lab session path

`src/lib/forge/sandbox/lab.server.ts`

The real-runtime path continues to obtain its binding through the server-only Supabase admin client. The caller no longer supplies ownership/node/environment metadata to the identity function; those values are derived authoritatively from `lab_instances` in the database.

## Important operational rule

The V49.1 package must never contain `.env.local` or any real Supabase/runtime secrets. The existing server-only secret configuration remains outside source control and outside release archives.
